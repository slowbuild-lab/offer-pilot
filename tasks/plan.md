# 智联招聘投递优化计划

日期：2026-10-20。状态：第一阶段已完成测试、构建与本机运行验收；第二、三阶段尚未开始。

## 目标与范围

先让投递可控、可停止、可追踪，再完善筛选和中断恢复。本计划针对本机 get_jobs 的智联招聘流程，沿用现有滚动加载、成功确认弹窗和 0–300 秒等待配置。任务清单与验收标准见 [todo.md](todo.md)。

本次不调整 BOSS、猎聘、前程无忧，不增加验证码绕过、自动解除平台限制或自动定时投递。这里只控制操作数量和节奏，遇到平台要求人工处理时暂停。

## 当前代码依据

- `ZhiLian.deliverByKeyword` 已支持滚动加载，每个关键词最多 50 批；批次限制不能代表实际投递数量。
- 新版列表仅用 `existsByJobId` 避免重复入库；是否投递仍主要看网页按钮，尚未依据本地已确认记录跳过投递。
- `ZhilianJobService` 通过布尔状态判断运行中，启动操作存在检查与异步执行之间的窗口；停止检查也需要覆盖投递按钮点击前。
- `deliveredCount` 在 worker 返回后赋值，运行中的确认成功数没有持续更新。
- `zhilian_data` 的更新时间会在标记已投递时改变，不能据此准确还原过去每日的投递次数。

## 实现约定

### 1. 数量限制与投递记录

前端明确显示“本次最多尝试投递”和“每日最多尝试投递”。建议默认分别为 20、50，作为可修改的初始配置，不是平台官方额度。有效范围计划为 1–500；本次额度可以大于当天剩余额度，但实际执行以先达到的限制为准。

数量以本工具实际发起的投递尝试计数，不以浏览数量、收集数量或确认成功数量计数。点击前在 SQLite 事务中占用额度并记录岗位，避免并发超额；点击成功发出后不因超时、取消或重启释放额度。能确定没有发出点击的失败可以释放预留；崩溃时无法确定的记录保留并进入待核实状态。已投递和筛选跳过的岗位不消耗额度。

每日边界采用 Asia/Shanghai，时间字段使用带明确时区的时间戳。统计覆盖本工具记录的尝试，不声称包含用户在其他设备或网页手动操作的次数。老记录继续用于历史去重，过去的每日尝试次数无法准确重建；功能启用当天页面显示统计起始时间，避免将历史操作解释为零。

增加智联专用的任务与尝试记录，不用修改既有记录的更新时间推算额度。对任务状态、记录状态和配置使用明确字段，不再通过中文消息里的“失败”等关键词推断任务状态。

### 2. 任务状态与停止

状态计划为：空闲、启动中、运行中、暂停中、已暂停、停止中、已停止、已完成、失败。服务端先原子占用任务，再安排异步执行；重复点击启动只产生一个任务。

在导航、加载等待、弹窗等待和真正投递前检查停止标志。停止不能撤回已经发出的申请；页面需要保留这类结果。停止后不执行新的投递点击，已开始的页面操作结束后再释放任务占用。

### 3. 去重与异常

以平台和岗位 ID 为准，先检查已确认投递、待核实及正在投递记录，再考虑按钮状态；不能仅因数据库存在一条“未投递”的采集记录就跳过。

遇到验证码、登录失效、平台投递限制或连续 3 次实际投递结果未确认／失败时暂停。主动停止、筛选跳过和历史去重不计入连续失败。正常采集成功不能清空投递失败计数，只有确认投递成功才清空。

页面展示暂停原因，用户处理后显式继续；平台明确达到当日上限时结束当日任务，不自动重试。结果未确认的岗位进入待核实列表，不自动重投。去重和额度查询、写入必须在点击前完成；数据库异常则停止操作并显示原因。

### 4. 筛选、预览与恢复

第一版筛选使用确定性规则：公司黑名单、排除关键词、城市、薪资、学历和经验。缺失、区间重叠或无法解析的条件标记“待确认”，不静默当成匹配，不引入 AI 自动判定。

预览模式只采集和筛选，不点击投递；预览结果记录采集时间，实际投递前再次核实岗位信息。筛选配置只影响下一次新任务；修改规则后恢复旧任务，需要重新预览或新建任务。

断点保存任务配置快照、岗位 ID 和处理结果，不保存网页卡片下标作为恢复依据。重启只提示有可恢复任务，不自动投递；恢复时重新检查登录、额度和待核实记录。

## 实施顺序

### 第一阶段：投递可控

1. 任务启动互斥与停止检查。
2. 持久化任务和尝试记录。
3. 前端数量限制配置与校验。
4. 点击前额度检查与跨重启统计。
5. 历史去重与待核实处理。
6. 异常自动暂停与人工继续。

每两项设一个检查点。阶段验收重点：双击启动不产生两个任务；额度用完后没有额外点击；重启后已确认和待核实岗位不会自动重投；异常出现后暂停且原因可见。

### 第二阶段：投递可解释

7. 实时计数、等待倒计时与任务结果。
8. 前端筛选规则。
9. 只预览再投递。

阶段验收重点：所有计数与尝试记录一致；跳过有原因；预览期间投递按钮点击次数始终为零。

### 第三阶段：中断可恢复

10. 从持久化记录恢复未处理岗位。

阶段验收重点：重启不会自动开始；用户继续后只处理尚未处理且符合规则的岗位；重复点击继续不会重复投递。

## 验证与交付

- 每项先写能复现问题的测试，再完成实现；涉及浏览器的行为采用本地隔离页面，使用临时数据库验证持久化与迁移。
- 验证数量边界、并发启动、跨日、重启、停止发生在点击前后、验证码、结果超时和数据库不可用等关键场景。
- 每个检查点运行对应回归测试，阶段结束强制重建前端并执行完整构建。
- 最终重启前确认任务空闲，保留现有数据库、浏览器配置和本地启动修改；检查旧 Java 与专用 Chrome 退出后再启动新版。
- 交付时检查健康接口、浏览器初始化完成日志、登录状态和新版前端。验证不提交真实简历；真实投递结果需要用户后续操作确认。
- 现有功能的既往测试结果不是新增优化的完成证明；每项只有实际验证通过后才勾选完成。

## 风险与处理

- 平台页面结构变化：用本地页面回归保护选择器；无法识别关键按钮或确认结果时停止并提示。
- 网络请求和本地数据库不能构成同一事务：使用点击前记录和待核实状态，优先避免重复投递，不承诺外部平台严格一次成功。
- 一次异常不代表没有发出申请：不自动重试待核实岗位，也不自动返还其额度。
- 老数据可能存在同岗位多行：查询时以岗位 ID 汇总已确认状态；先检查数据，再考虑增加约束，不删除历史记录。
- 当前多个文件已有本次会话的修改：逐项增量实现，禁止重置工作区或覆盖原数据库。
